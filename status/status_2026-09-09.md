## Summary

## Completed this run

- `reports/exporter.py` (new): `export_csv()` and `export_json()`, matching
  the exact column order (section 15.1) and JSON shape (section 15.2) the
  spec defines. Pure formatting/I/O -- no hashing, filesystem, or
  comparison logic, consistent with the layered architecture (section 5).
- `gui/dialogs.py`: added `choose_save_file()`, a thin `asksaveasfilename`
  wrapper alongside the existing folder-picker/confirmation/error dialogs.
- `gui/main_window.py`: "Export CSV" / "Export JSON" buttons under the
  results table, enabled once a scan completes and disabled again whenever
  the active baseline changes (a new folder is selected, or a new baseline
  is created) so a stale scan can never be exported silently. Export
  failures (e.g. permission denied on the chosen path) are caught and
  shown as a friendly dialog rather than crashing, per section 18, and
  logged with `exc_info` (section 16: "Export operations").
- `tests/test_reports.py` (new): the section 19 "Reports" minimum coverage
  -- CSV generation, JSON generation, correct summary counts, correct file
  paths, and valid JSON syntax (`json.loads` round-trip), plus empty-result
  and missing-hash/size edge cases.
- `tests/test_gui_integration.py`: added the Run 6 acceptance scenario
  (scan -> export CSV -> export JSON, with the exported files' contents
  verified) and a test that switching folders clears the export buttons'
  enabled state.

## Explicitly deferred

- **Scan history UI.** Listed as a Run 6 objective, but not required by
  the Run 6 acceptance criteria (section 31: "Scan -> View results ->
  Export CSV -> Export JSON") nor by the Definition of Done (section 40).
  `storage.repository.list_scans` / `get_scan_results` (Run 4) already
  provide everything a future history view would need; adding UI for it
  now would expand this run's scope beyond what the spec requires
  (section 38's scope-control rule). Left for a future run if desired.
- **Scheduled scanning.** Explicitly optional (section 20, section 31:
  "If Run 6 cannot implement it reliably, defer it... this feature must
  not compromise the core application"). Deferred to keep this run's
  surface area small and the reporting feature well-tested; Windows Task
  Scheduler integration (`schtasks /create ...` invoking the packaged
  `.exe` with a scan action) remains the preferred approach if implemented
  later, rather than a custom in-process scheduler daemon.

## Notes / decisions

- CSV/JSON export operate on the in-memory results of the most recently
  completed scan, not an arbitrary past scan from history -- consistent
  with deferring the scan-history UI above. `storage.repository` already
  supports re-loading any past scan's results by id, so wiring a "export
  this historical scan" action later is a small addition, not a redesign.
- `ScanResult` has no per-file timestamp (a Run 4 decision carried
  forward); as in the results table, CSV rows use the scan's single
  completion timestamp for every row, matching section 15.1's example
  header literally (`status,path,baseline_hash,current_hash,size,timestamp`).
- Export buttons are wired through the same `_set_controls_enabled` /
  `_start_background_task` plumbing as the rest of the window, so they are
  correctly disabled while a scan or baseline creation is in progress and
  restored afterward based on whether a completed scan is available.
