## This run's change

`pytest-cov` showed `app.py` at 0% coverage (21/21 statements missed) —
the one production module no test ever imported, since importing it
pulls in `customtkinter`/`tkinter` and calls `configure_logging()`
against the real per-user app-data directory unless mocked.

Added two tests to `tests/test_foundation.py` (which already owns the
Run 1 foundation tests), each guarded with
`pytest.importorskip("tkinter")` / `pytest.importorskip("customtkinter")`
like the rest of the GUI-adjacent suite, and monkeypatching
`app.configure_logging` / `app.MainWindow` at the exact seam `app.py`
calls through — the same pattern used throughout the suite for GUI/core
seams:

- `test_app_main_configures_logging_builds_window_and_runs_loop` —
  confirms `main()` configures logging once, builds exactly one
  `MainWindow`, calls its `mainloop()`, and returns exit code `0`.
- `test_app_main_logs_and_reraises_when_window_creation_fails` —
  confirms a failure constructing the main window is logged (section 16)
  and re-raised rather than swallowed.

Neither test builds a real Tk window or touches the real application
data directory.

## Environment note

This container did not have `tkinter` available for its default Python
3.11 interpreter, and did not have it available at all until
`python3-tk`/`python3.12` were installed via `apt-get`. Prior runs'
containers apparently had this preinstalled. This is worth knowing for
future scheduled runs: a `63 passed / 31 skipped` result under
`xvfb-run` (instead of the expected ~100 passed) means `tkinter` isn't
actually present, not that the real-display suite is failing.
