## Push target discrepancy (needs owner attention)

While checking the branch/push convention that Runs 18-21 disagreed
about, this run compared `origin/main` against the actual commit history
directly (`git ls-remote`, not just trusting prior status reports) and
found:

- `origin/main` is currently at **Run 17** (`72fedb1`).
- Runs 18, 19, 20, and 21's commits exist only on per-run scratch branches
  (`claude/elegant-hopper-*`) — `main` is **four commits behind** the
  actually-verified history.
- Run 20's and Run 21's own status reports both state that they
  fast-forwarded `origin/main` to include their work. Neither push
  appears to have actually landed on `main` — there is no evidence in the
  remote history that it ever moved past Run 17. The stored task prompt's
  "Always push to main branch... Force push if needed" instruction and
  this session's assigned-branch policy ("develop on
  `claude/elegant-hopper-*`, never push elsewhere without explicit
  permission") are in direct conflict, and prior runs alternated between
  them without the discrepancy being caught.

Given that conflict, and that force-pushing to `main` is a shared,
hard-to-reverse operation, this run did **not** attempt to push to `main`
or repeat an unverified claim of having done so. This run's commits
(this status report and the spec update) were pushed only to this
session's assigned branch. **The repository owner should decide and fix
`main` directly**: either fast-forward it to the latest verified commit,
or confirm that scratch-branch-only pushes are intentional (in which case
`main` being stale is expected and the stored task prompt should be
updated to stop asking for pushes to `main`).
