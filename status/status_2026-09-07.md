## Completed this run

- `storage/database.py`: SQLite connection management and schema. Defines
  the `baselines`, `baseline_files`, `scans`, and `scan_results` tables
  from `PROJECT_SPEC.md` section 14 in one place (schema only -- no
  scan-related read/write logic yet, per scope control). `connect()` is a
  context manager that opens, initializes, and guarantees closing a
  connection. A database file that exists but is not valid SQLite raises
  `DatabaseCorruptedError` instead of crashing (section 19: "Corrupted
  baseline is handled").
- `storage/repository.py`: baseline data-access functions --
  `insert_baseline()`, `get_latest_baseline_id()`,
  `get_baseline_metadata()`, `get_baseline_files()`. Each call to
  `insert_baseline()` creates a new row rather than overwriting a prior
  baseline, so scan history against earlier baselines remains possible.
- `core/baseline.py`: the `Baseline` dataclass (root directory, created-at
  timestamp, application version, files, optional id) plus:
  - `create_baseline()` -- enumerates and hashes a directory via
    `core.filesystem.scan_directory()` and returns an in-memory
    `Baseline` (not yet persisted) alongside any unreadable-file errors,
    so the GUI can show a confirmation before committing (section 9).
  - `save_baseline()` -- persists a `Baseline` via the repository layer.
  - `load_baseline()` -- loads the latest baseline, or a specific one by
    id; raises `BaselineNotFoundError` when none exists or the requested
    id is unknown (section 19: "Missing baseline is handled").
- `tests/test_baseline.py`: the full Run 3 acceptance scenario from
  section 28 (create directory → create files → create baseline → modify
  filesystem → reload baseline, confirming the reloaded baseline reflects
  the file state *at baseline time*), plus baseline round-tripping,
  multiple baselines never overwriting each other, missing-baseline and
  unknown-baseline-id handling, corrupted-database handling, and
  unreadable files being excluded from the baseline while still reported
  as errors.
- Updated `PROJECT_SPEC.md` progress line and `README.md` status banner.

## Notes / decisions

- `core/baseline.py` depends on `storage.repository`, following the
  layered architecture in spec section 5 (GUI → application logic →
  core/security logic → storage), where each layer may call the one
  below it.
- `create_baseline()` and `save_baseline()` are separate functions so
  baseline creation can be tested and previewed (file count, timestamp)
  without requiring a database, and so the GUI (Run 5) can insert its
  "this replaces the active baseline" confirmation between the two calls
  per section 9.
- `insert_baseline()` always creates a new baseline row rather than
  updating one in place. This keeps prior baselines loadable by id (used
  by scan history in a later run) and pushes the "warn before replacing"
  UX decision to the GUI layer, where it belongs.
