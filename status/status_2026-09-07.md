## Completed this run

- `core/models.py`: added the `Baseline` dataclass (baseline_id,
  created_at, root_directory, application_version, files), per spec
  section 6.2.
- `storage/database.py`: `connect()` / `initialize_schema()` -- opens (and
  creates if needed) the local SQLite database, with `sqlite3.Row` row
  access and foreign keys enabled. Creates all four recommended tables
  from spec section 14 (`baselines`, `baseline_files`, `scans`,
  `scan_results`) up front, since the schema is specified together and
  `CREATE TABLE IF NOT EXISTS` makes this idempotent -- Run 4/6 will
  populate `scans`/`scan_results` without a schema migration.
- `storage/repository.py`: `save_baseline()`, `load_baseline()`,
  `load_latest_baseline()`, `has_any_baseline()` -- all baseline SQL lives
  here, translating to/from `core.models.Baseline`/`FileRecord`. Each
  baseline creation inserts a new row rather than overwriting, so prior
  baselines remain as history; "current" is simply the most recent.
- `core/baseline.py`: `create_baseline()` (scans + hashes via
  `core.filesystem.scan_directory`, then persists via the repository, and
  returns unreadable files as errors separate from the baseline itself),
  `has_existing_baseline()` (for the GUI to warn before replacement, spec
  section 9), `load_baseline()` / `load_latest_baseline()`, and
  `open_database()`. Missing/unknown baselines and a corrupted database
  file are wrapped in a friendly `BaselineLoadError` rather than a raw
  `sqlite3`/traceback (spec section 18 and section 19's "missing baseline
  is handled" / "corrupted baseline is handled").
- `tests/test_baseline.py`: baseline creation, the full
  create → modify filesystem → reload → unchanged flow from section 28's
  acceptance criteria, `has_existing_baseline` state transitions, latest-
  vs-specific-id loading, unknown baseline id, a corrupted database file,
  and unreadable files being excluded from the baseline and reported as
  errors.
- Updated `PROJECT_SPEC.md` progress line and `README.md` status banner.

## Verification performed

- `pytest -q` (full suite): **27 passed, 4 skipped**. The skips are the
  permission-error tests (hashing, filesystem, and now baseline) that
  cannot run meaningfully under this container's root user, since
  `chmod 0` does not block root from reading a file -- consistent with the
  Run 2 status report and confirmed again via `id`/`whoami`.
- Manually reasoned through the corrupted-database case: a file containing
  non-SQLite bytes at the database path causes `sqlite3` to raise
  `DatabaseError` as soon as the schema is applied; `open_database()`
  catches this and raises `BaselineLoadError` with a user-facing message,
  which the new test asserts directly.

## Notes / decisions

- `core/baseline.py` has no SQL of its own and `storage/repository.py` has
  no filesystem/hashing logic, preserving the GUI → logic → core → storage
  layering from spec section 5.
- Baseline history is kept (each `create_baseline()` call adds a new row)
  rather than overwriting in place; this is simpler than in-place
  replacement, still satisfies "prevent accidental silent replacement"
  (that check belongs to the Run 5 GUI, via `has_existing_baseline()`),
  and costs nothing extra at MVP scale.
- The full section 14 schema (including `scans`/`scan_results`) was
  created now rather than deferred to Run 4, to avoid a schema-migration
  step later; no scan logic was implemented against those tables this run.
