## Completed this run

- `core/models.py`: added the `Baseline` dataclass (section 6.2) --
  `baseline_id`, `created_at`, `root_directory`, `application_version`,
  and a tuple of `FileRecord` files.
- `core/baseline.py`:
  - `create_baseline()` -- builds an unsaved `Baseline` from a directory
    using the Run 2 `scan_directory()` engine; returns `(baseline,
    errors)` so unreadable files can be reported without failing baseline
    creation (section 7.3).
  - `validate_baseline()` -- rejects a `Baseline` with a missing
    root/timestamp, malformed file entries, duplicate paths, or an
    invalid hash length, raising `BaselineError`. Used on every load so a
    corrupted baseline is reported cleanly instead of crashing the app
    (section 19).
  - `BaselineError` -- the user-facing exception for baseline
    create/save/load failures.
- `storage/database.py`: SQLite schema for all four tables from section
  14 (`baselines`, `baseline_files`, `scans`, `scan_results`) and
  `get_connection()`/`initialize_schema()`. `scans`/`scan_results` are
  defined now for a single source of schema truth but stay unused until
  the scan engine (Run 4). Foreign keys are enabled explicitly.
- `storage/repository.py`: `BaselineRepository` with `save_baseline()`
  (single transaction for the baseline row + all file rows),
  `load_baseline(id)`, `load_latest_baseline()`, and `has_baseline()`
  (for the GUI's "warn before replacing an existing baseline" prompt in
  Run 5). Database errors (corrupted/unwritable file) and malformed rows
  are caught and re-raised as `BaselineError` with the original exception
  chained for the log.
- `tests/test_baseline.py`: baseline creation, save/load round-trip,
  loading the most recent of several baselines, the section 28 acceptance
  scenario (create → save → modify filesystem → reload baseline
  unchanged), a missing baseline, a corrupted database file, a corrupted
  baseline row, and `validate_baseline()` accept/reject cases.
- Updated `PROJECT_SPEC.md` / `SentinelLite.md` progress lines and the
  `README.md` status banner.

## Notes / decisions

- `core/baseline.py` has no storage or GUI dependency; `storage/
  repository.py` has no hashing/filesystem or GUI dependency -- preserves
  the layered architecture in spec section 5.
- `save_baseline()` writes the baseline row and every file row in one
  SQLite transaction, so a failure partway through cannot leave a
  half-written baseline in the database.
- Baseline validation runs on every load (not just save), which is what
  turns a corrupted database row into a friendly `BaselineError` instead
  of a crash or, worse, silently trusting bad data as the baseline.
