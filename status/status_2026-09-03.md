# SentinelLite — Status Report

## Summary

This run implements PROJECT_SPEC.md section 27 (Run 2): the core
SHA-256 hashing and recursive filesystem enumeration engine. Run 1's
foundation (app entry point, config, logging, GUI shell) was inspected
and left unchanged; its four tests still pass. No baseline, scan

scoped to Runs 3-5.

## Completed this run

- `core/models.py`: `FileRecord` (path/sha256/size/modified_time, per
  spec section 6.1) and `FileAccessError` (path/message) dataclasses.
  Also added `ScanStatus` (`NEW`/`MODIFIED`/`DELETED`/`UNCHANGED`/`ERROR`,
  per section 6.3) here since it is shared core data model, not
  comparison logic -- the scan engine (Run 4) will consume it rather than
  redefine it.
- `core/hasher.py`: `calculate_sha256()` -- SHA-256 via `hashlib`,
  incremental/chunked reads (default 1 MiB, from `config.DEFAULT_HASH_CHUNK_SIZE`),
  so files are never fully loaded into memory. Handles empty files.
  Raises `OSError` on unreadable files rather than swallowing errors --
  callers decide how to handle failures (per spec section 7.3).
- `core/filesystem.py`:
  - `enumerate_files()`: recursive traversal via `os.walk`. Symbolic
    links (files and directories) are **not** followed by default --
    documented decision per spec section 8.2, since safety of following
    links has not been established. Directory-listing permission errors
    are caught via `os.walk`'s `onerror` hook, logged, and skipped
    rather than aborting the walk (section 8.3).
  - `build_file_record()`: hashes + stats one file, returning a
    `FileRecord` with a forward-slash relative path (section 6.2).
  - `scan_directory()`: enumerates and hashes every file under a root,
    catching per-file `OSError`s (permission denied, file removed
    mid-scan, etc.) as `FileAccessError` entries instead of crashing the
    scan (section 7.3), with an optional progress callback
    (`processed, total, path`) for the future GUI progress bar (Run 5).
- `tests/test_hasher.py`: identical files hash identically, a modified
  file hashes differently, hash matches a `hashlib` reference, empty
  files, large files hashed correctly regardless of chunk size, and
  invalid-chunk-size / missing-file error cases.
- `tests/test_filesystem.py`: recursive enumeration against the
  directory tree shown in spec section 8, relative-path `FileRecord`
  production, progress-callback behavior, permission-denied files are
  skipped and reported while the rest of the scan continues, and that
  both symlinked files and symlinked directories are not followed.
  (Not in the spec's suggested test file list, which only names
  `test_hasher.py`; filesystem-traversal behavior is different enough
  from pure hashing to warrant its own file -- per spec section 5, the
  exact structure may be adjusted for a strong technical reason.)

## Notes / decisions

- `os.walk(followlinks=False)` plus explicit `is_symlink()` checks (for
  both files and the in-place `dirnames` prune) is the chosen symlink
  policy -- simplest correct option that satisfies section 8.2 without
  adding a dependency.
- Error messages surfaced from the filesystem layer use the
  user-friendly wording from section 18 ("Unable to read file: ...");
  the underlying `OSError` is logged instead of shown to the user.
- `ScanStatus` was added to `core/models.py` now (rather than waiting for
  Run 4) purely as a shared enum with no comparison logic attached --
  this keeps section 6's data model together in one place without
  implementing any scanning behavior early.
