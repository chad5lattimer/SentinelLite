# SentinelLite — Status Report

**Date:** 2026-09-03
**Run:** 2 — Hashing and Filesystem Engine

## Summary

This run implements the Run 2 objectives from `PROJECT_SPEC.md` section 27:
the core SHA-256 hashing utility and the recursive filesystem enumeration
engine. Run 1's foundation (structure, config, logging, window shell) was
verified still intact and correct before starting; no changes to it were
needed.

## Completed this run

- `core/models.py`: `FileRecord` dataclass (path, sha256, size,
  modified_time) per spec section 6.1; `FileError` (path, message) for
  unreadable files per section 7.3; `ScanStatus` enum
  (NEW/MODIFIED/DELETED/UNCHANGED/ERROR) per section 6.3, added now since
  it is part of the same core data model and will be consumed unchanged by
  the baseline/scanner work in Runs 3-4.
- `core/hasher.py`: `calculate_sha256()` — chunked, incremental SHA-256
  hashing via `hashlib`, default chunk size from `config.DEFAULT_HASH_CHUNK_SIZE`
  (1 MiB). Never loads a full file into memory. Read errors propagate as
  `OSError` rather than being swallowed, so callers can record them per
  section 7.3.
- `core/filesystem.py`:
  - `iter_files()` — recursive traversal via `os.walk`; permission errors
    on directories are logged and skipped rather than aborting the walk
    (section 8.3).
  - `build_file_record()` — hashes one file and returns a `FileRecord`
    with a relative, forward-slash-normalized path (section 6.2).
  - `scan_directory()` — enumerates and hashes every file under a root,
    returning `(records, errors)`; a single unreadable file is recorded
    as a `FileError` and does not stop the scan (sections 7.3, 8.3).
    Accepts an optional `on_progress(done, total, current_path)` callback
    so a future GUI can drive the progress display in section 13 without
    this module depending on the GUI.
  - **Symbolic link policy (section 8.2, documented as required):**
    symlinked files and directories are **not followed** by default. A
    directory symlink could point outside the monitored root or create a
    cycle, and a file symlink could hash content living outside the
    monitored tree; both are skipped and logged. Overridable via
    `follow_symlinks=True` for callers that have determined it's safe.
- `tests/test_hasher.py`: same-file/modified-file hashing, empty file,
  multi-chunk large file (hashed with two different chunk sizes, results
  compared against `hashlib` directly), digest shape, unreadable-file
  error, invalid chunk size.
- `tests/test_filesystem.py`: recursive enumeration over a nested tree,
  empty directories, relative-path `FileRecord` construction, full
  `scan_directory` over a tree, progress-callback behavior, continuing
  past an unreadable file (POSIX-only, skipped when running as root),
  and both symlink cases (file and directory) are not followed by
  default (POSIX-only).

## Notes / decisions

- `models.py` also defines `ScanStatus`/`FileError` slightly ahead of
  strict Run 2 scope, since they are trivial, GUI-independent additions
  to the same "core data model" section of the spec (section 6) and avoid
  churn when Runs 3-4 need them. No baseline, storage, or scanning
  *behavior* was implemented — only these small shared types.
- Progress reporting in `scan_directory` does two passes conceptually
  (enumerate fully, then hash with a known total) so the GUI can show
  "N / total" per section 13; this matches the spec's allowance that
  "the exact progress calculation may be approximate if necessary" while
  keeping the common case exact.
