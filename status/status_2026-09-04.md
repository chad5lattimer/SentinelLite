## Completed this run

- `core/models.py`: `FileRecord` (path, sha256, size, modified_time per
  PROJECT_SPEC.md section 6.1/6.2) and `FileAccessError` (path, error) as
  frozen dataclasses. No filesystem or hashing logic -- data structures
  only.
- `core/hasher.py`: `calculate_sha256()` -- incremental, chunked SHA-256
  hashing via `hashlib`, using `config.DEFAULT_HASH_CHUNK_SIZE` (1 MiB) as
  the default chunk size (section 7.2). Raises `OSError` on read failure
  rather than swallowing it; callers decide how to handle that.
- `core/filesystem.py`:
  - `enumerate_files()`: recursively walks a directory (`os.walk`,
    `followlinks=False`), yielding regular files and skipping symbolic
    links entirely (see the documented policy below). Directories that
    cannot be listed are logged via the `onerror` callback and skipped
    without stopping the rest of the walk (section 8.3).
  - `build_file_record()`: hashes one file and returns a `FileRecord` with
    a root-relative, forward-slash path.
  - `scan_directory()`: orchestrates enumeration + hashing for an entire
    directory tree, catching `OSError` per file so one unreadable/vanished
    file does not abort the run -- it is logged and returned as a
    `FileAccessError`, and processing continues with the remaining files
    (sections 7.3/8.3).
- `tests/test_hasher.py` (11 new tests): same-file hash stability, a
  modification changing the hash, hashing an empty file, hashing a file
  incrementally across many small chunks (verified against a direct
  `hashlib.sha256` digest), a missing file raising `OSError`, chunk-size
  validation, recursive nested-directory enumeration, symlink skipping,
  `FileRecord` field correctness, and that `scan_directory` continues past
  an unreadable file and reports it as a `FileAccessError`.

## Design decisions

- **Symbolic links (PROJECT_SPEC.md section 8.2):** SentinelLite does not
  follow symbolic links, for either files or directories. They are
  detected with `Path.is_symlink()`, logged at `INFO`, and skipped
  entirely -- never hashed, never reported as an error. This avoids a scan
  silently leaving the monitored directory (or looping via a self-
  referential symlink), which would undermine the integrity guarantee the
  baseline is meant to provide. Documented here and in the module
  docstring of `core/filesystem.py`.
- **Permission-error test strategy:** the automated test environment runs
  as `root`, where standard Unix permission bits (`chmod 000`) do not
  actually block reads, so a literal permission-denied test would be
  unreliable in CI. `test_scan_directory_continues_after_unreadable_file`
  instead monkeypatches `enumerate_files` to include a path that does not
  exist, which exercises the identical `OSError`-handling/continue path
  that a real `PermissionError` would take. The Windows target platform
  and non-root development use are expected to exercise the real
  permission-denied path; the handling code itself does not distinguish
  between error causes.
- Kept `core/models.py` to just `FileRecord` and `FileAccessError` this
  run. `ScanStatus`/scan-result structures (section 6.3) are deferred to
  Run 4 (`core/scanner.py`), where they are actually used, per the spec's
  scope-control rule (section 38).
