## Completed this run

- `core/models.py`: `FileRecord` dataclass (`path`, `sha256`, `size`,
  `modified_time`), per PROJECT_SPEC.md section 6.1/6.2. Relative paths
  use forward slashes for cross-platform consistency.
- `core/hasher.py`: `calculate_sha256()` -- incremental, chunked SHA-256
  hashing (default 1 MiB chunks, configurable) so files are never fully
  loaded into memory (section 7.2). Unreadable files raise `HashError`
  rather than crashing (section 7.3).
- `core/filesystem.py`: `enumerate_files()` -- recursively walks a
  directory, hashes every regular file, and returns an
  `EnumerationResult` of `FileRecord`s plus `FileError`s for anything
  that could not be read. Permission errors on individual files or
  subdirectories are logged and skipped rather than aborting the walk
  (sections 7.3, 8.3). Symbolic links are never followed (documented
  decision per section 8.2, to avoid link cycles and files escaping the
  monitored directory).
- `tests/test_hasher.py`: same-file/modified-file hashes, known SHA-256
  test vectors, empty file, large file with a small chunk size (proves
  chunking doesn't change the digest), missing/unreadable file ->
  `HashError`, invalid chunk size rejected.
- `tests/test_filesystem.py`: flat and nested enumeration, forward-slash
  relative paths, hash/size correctness, empty directory, nonexistent
  root, unreadable file/directory recorded as errors while the scan
  continues, symlinks (to files and directories) are skipped and not
  followed.
- `README.md` and spec progress line updated to reflect Run 2 completion.

## Notes / decisions

- Symbolic links are skipped entirely rather than followed, per the
  spec's guidance to "avoid recursively following symbolic links unless
  explicitly determined to be safe" (section 8.2). This is the simplest
  safe behavior and is documented here and in `core/filesystem.py`'s
  module docstring, per the spec's rule for resolving ambiguity
  (section 37).
- `FileError` (in `core/filesystem.py`) is a new, minimal type distinct
  from the `ScanResult`/status model in section 6.3 -- that model
  (NEW/MODIFIED/DELETED/UNCHANGED/ERROR statuses) belongs to the
  comparison engine and is deferred to Run 4 (`core/scanner.py`) to
  avoid expanding this run's scope.
- `core/models.py` intentionally contains only `FileRecord` for now;
  the `ScanResult`/status enum described in spec section 6.3 will be
  added alongside the scanner in Run 4, when it is actually consumed.
