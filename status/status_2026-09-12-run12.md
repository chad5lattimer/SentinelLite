## Work performed this run

1. **Installed `pytest-cov` and measured coverage** across `core`,
   `storage`, `reports`, `config`, and (under `xvfb-run` with a
   `python3.12` + `tkinter` + `customtkinter` virtualenv) `gui`. Before any
   change: `config.py` 93%, `core/baseline.py` 93%, `core/filesystem.py`
   90%, `gui/main_window.py` 92%, `gui/results_view.py` 94%; everything
   else already 100%.

2. **Closed three of those gaps with additive tests, no production
   behavior changed:**
   - `tests/test_foundation.py`: three new tests for
     `config._default_app_data_dir`'s Windows (`%LOCALAPPDATA%`, with and
     without the environment variable set) and macOS
     (`~/Library/Application Support`) branches, monkeypatching
     `sys.platform` so they run on this Linux container. `config.py` is
     now 100%.
   - `tests/test_baseline.py`: one new test for
     `core.baseline.find_baseline_for_directory`'s defensive
     race-condition branch -- the per-directory index still names a
     baseline id, but the baseline row itself is gone by the time it is
     loaded (e.g. deleted between the id lookup and the load). Must
     return `None`, not let `BaselineNotFoundError` propagate.
   - `tests/test_gui_integration.py`: one new test for
     `gui/results_view.py`'s column-header sort (`ResultsView._sort_by`,
     wired to the treeview headings) -- clicking a column heading sorts
     the visible rows by that column and clicking it again reverses the
     order (PROJECT_SPEC.md section 12: "sortable ... table").
     `gui/results_view.py` is now 100%.

   The two remaining gaps (`core/baseline.py` lines 113-114,
   `core/filesystem.py` lines 53/116-118) are permission-error logging/
   handling branches that only execute when the filesystem actually
   enforces permission bits for a non-root user -- this container runs
   tests as root, so `chmod(0)` does not block reads and the existing
   tests for these paths (`test_scan_directory_continues_after_permission_error`,
   etc.) already skip themselves accordingly. Not a real gap; a CI
   environment running as a non-root user would already cover them.

3. **Found and fixed a real bug while adding the sort test.** Writing
   that test exposed a genuine, narrow race: closing the main window
   while a background scan/baseline thread is still running lets that
   thread's completion callback (`self.after(...)` in
   `MainWindow._start_background_task`) fire after `destroy()` has torn
   down the window's Tcl interpreter, raising an unhandled
   `RuntimeError`/`TclError` **on the worker thread itself** -- exactly
   the kind of silent-looking failure PROJECT_SPEC.md section 35 warns
   against, and section 18's "errors must be user-friendly" extends in
   spirit to a background thread with nobody left to show an error to.
   Fixed by adding `MainWindow._after_safe`, which wraps every
   `self.after(...)` call in `_start_background_task` (both the progress
   callback and the two completion callbacks) and logs-and-drops the
   race instead of letting it escape. Added
   `tests/test_gui_integration.py::test_after_safe_swallows_a_destroyed_windows_after_call`
   (parametrized over both exception types) as a regression test; it
   calls `MainWindow._after_safe` against a minimal stand-in object
   rather than actually creating and destroying a real `MainWindow`,
   deliberately avoiding any dependency on real widget-destruction
   timing -- an earlier version of this test that did destroy a real
   window was empirically shown (over 10-30 repeated runs) to
   occasionally destabilize the timing-sensitive `_pump_until` polling
   used by other tests in the same file, so it was rewritten before being
   committed. Verified this test fails without the fix (`AttributeError:
   no attribute '_after_safe'` against the pre-fix code) and passes with
   it.
