## Verification performed

This container has no `tkinter` for the Python build `pytest` normally
runs under (consistent with prior runs' notes) -- GUI tests skip there, as
before. Because Run 5 is GUI-heavy, that skip is not enough evidence on
its own, so this run additionally installed a system Python 3.12 with
`tkinter`/`customtkinter` and an `Xvfb` virtual display, and ran the full
suite for real:

- `pytest -q` (project's normal interpreter, no display): **36 passed, 11
  skipped** -- no regressions; the 6 new GUI-skip cases join the prior 5.
- `xvfb-run pytest -q` (Python 3.12 + tkinter + customtkinter + virtual
  display): **43 passed, 4 skipped**. All 10 GUI tests actually executed
  a real `MainWindow`, a real background thread, and a real Tk event
  loop end-to-end. The 4 skips are the pre-existing root/chmod cases.

This real-display run caught two genuine bugs that a skip-only run would
have missed entirely, both fixed in `gui/main_window.py`:

1. **Shared SQLite connection used from a background thread.**
   `sqlite3` connections default to `check_same_thread=True`; the worker
   thread running a baseline/scan raised `sqlite3.ProgrammingError` the
   moment it tried to save. Fixed by having background workers open their
   own short-lived connection to the same database file
   (`storage.database.connect`) instead of sharing `self._connection`,
   which is now used only from the GUI thread.
2. **`except ... as error` used inside a closure invoked later.**
   Python deletes the `except`-clause binding when the block exits, so
   the `lambda: self._finish_background_task(on_error, error)` scheduled
   via `self.after(...)` raised `NameError` once actually invoked. Fixed
   by copying the exception to a plain variable before building the
   closure.

A related smaller finding: `logger.exception(...)` in the `on_error`
handlers ran outside the original `except` block (they run later, on the
GUI thread via `after`), so `sys.exc_info()` was empty and every failure
logged as `NoneType: None`. Switched to `logger.error(..., exc_info=error)`,
which logs the real traceback regardless of the active exception context.

Also manually confirmed:

  baseline untouched; accepting it creates a new one.
- Scanning after the monitored directory is deleted shows "Scan Error"
  and a friendly dialog rather than crashing (section 18).

## Notes / decisions

- SentinelLite tracks one active baseline per monitored folder, not per
  application session: selecting a folder looks up that folder's own most
  recent baseline (`find_baseline_for_directory`), so switching between
  two already-baselined folders finds the right one each time rather than
  only ever considering the single most recently created baseline
  overall.
- Progress reporting is intentionally approximate (indeterminate bar +
  running count), per section 13's explicit allowance, to avoid a second
  full directory walk purely to compute a total up front.
- The results table's "Timestamp" column shows the scan's completion time
  for every row (per-file modification time isn't part of `ScanResult`);
  documented here as a simplification rather than expanding `ScanResult`'s
  shape mid-run.
- `gui/main_window.py` still owns exactly one long-lived SQLite
  connection, used only from the GUI thread; background tasks now open
  and close their own connection per operation (see bug #1 above). This
  keeps `core.baseline`/`core.scanner`'s existing "caller passes a
  connection" signatures unchanged.
