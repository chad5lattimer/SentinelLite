# SentinelLite — Status Report

**Date:** 2026-09-08
**Run:** 5 — GUI Integration

## Summary

Verified Runs 1-4 (Foundation, Hashing/Filesystem Engine, Baseline
System, Comparison and Scan Engine) are intact and passing, then
implemented Run 5 per `PROJECT_SPEC.md` section 30: wired the core
engine (`core.baseline`, `core.scanner`) and storage layer into the
CustomTkinter GUI built in Run 1. A user can now perform the entire
workflow through the GUI: launch, select a folder, create a baseline,
change a file, scan, and see the MODIFIED result — without the window
ever freezing during a scan.

This container has no system `tkinter`, so GUI code could not previously
be exercised, only skipped (`pytest.importorskip("tkinter")`). This run
installed `python3-tk` + a Python 3.12 venv and used `xvfb-run` to
actually run the full GUI test suite headlessly against a real display,
rather than relying on skips alone.

## Completed this run

- `gui/main_window.py`: wired to `core.baseline` / `core.scanner`:
  - Folder picker (`tkinter.filedialog.askdirectory`).
  - **Create Baseline**: confirms before replacing an existing baseline
    (section 9), runs on a background thread, shows the "Baseline
    Created" summary (directory/files/created/status), and warns if any
    files were unreadable and excluded.
  - **Scan Now**: runs on a background thread, persists scan history,
    updates the results table, and sets the prominent security-status
    indicator (`✓ NO CHANGES DETECTED` / `⚠ CHANGES DETECTED` /
    `⚠ Scan Completed With Errors` / `✕ SCAN ERROR`, section 11.2/24).
  - Background worker plumbing (`_run_worker`/`_poll_worker`): a
    `threading.Thread` plus `queue.Queue`, polled via `self.after(...)`
    on the GUI thread — the scan/hash work never touches Tk widgets
    directly, and the GUI never blocks (section 13). Buttons disable
    during a running operation and re-enable via the same state-refresh
    path used everywhere else (`_update_controls`).
  - Progress display: an indeterminate progress bar plus a live
    "Files processed: N" / "Current file: ..." readout. A fixed
    denominator ("N / total") would need a throwaway pre-count pass
    before hashing even starts; section 13 explicitly allows an
    approximate progress calculation, so this was skipped as
    unnecessary complexity.
  - All eight application states from section 24 are represented (no
    folder / folder, no baseline / baseline ready / scanning / no
    changes / changes found / scan errors / fatal DB error).
  - The most recently created baseline (and its latest scan, if any) is
    reloaded automatically on startup, so "Baseline Ready" and prior
    results survive an application restart instead of forcing the user
    to recreate a baseline every launch.
  - Selecting a different folder than the active baseline's clears the
    active baseline client-side (it remains in scan history) rather than
    leaving "Scan Now" silently pointed at the old directory —
    `core.scanner.run_scan` always scans `baseline.root_directory`, so
    this keeps the button's behavior unambiguous.
- `gui/results_view.py` (new): summary counts (Modified/New/Deleted/
  Unchanged/Errors), a segmented All/Modified/New/Deleted/Unchanged/
  Errors filter, and a sortable `ttk.Treeview` results table with the
  Status/File/Baseline Hash/Current Hash/Size/Timestamp columns from
  section 12. `filter_results()` is a standalone pure function so the
  filtering logic is unit-testable without a widget.
- `gui/dialogs.py` (new): the baseline-replacement confirmation, the
  "Baseline Created" info dialog, and user-friendly error/warning
  dialogs (section 18) — no raw tracebacks are ever shown to the user.
- `tests/test_gui_integration.py` (new): drives the exact end-to-end
  workflow from section 30's acceptance criteria through the real
  widgets (folder → baseline → file change → scan → MODIFIED result),
  plus no-change / new+deleted / folder-switch / restart-restores-
  baseline scenarios. Modal dialogs are monkeypatched to avoid blocking
  on user input; background-thread completion is awaited by pumping
  `window.update()` in a loop rather than calling `mainloop()`.
- `tests/test_results_view.py` (new): unit tests for `filter_results()`
  against all six filter options.
- `tests/test_foundation.py`: updated the Run 1 GUI smoke test for the
  Run 5 behavior change — `Change Folder` is now enabled as soon as the
  window opens (folder selection no longer requires anything else first,
  per section 24's "No folder selected" state), and the test now points
  the window at a temporary database rather than the real per-user data
  directory, since `MainWindow` now opens a database connection on
  construction.
- Updated `PROJECT_SPEC.md`, `SentinelLite.md`, and `README.md` progress
  banners; documented the `python3-tk` system-package requirement for
  Linux development.

## Verification performed

- `pytest -q` in this container (no system `tkinter`): **35 passed, 11
  skipped** (up from 5 skips — the new GUI-only tests skip the same way
  the existing ones do; no non-GUI regressions).
- Installed `python3-tk` + a Python 3.12 venv (`customtkinter`, `pytest`)
  and ran the full suite under `xvfb-run` (a real, if virtual, display):
  **49 passed, 4 skipped** — every GUI and integration test actually
  executed, not just skipped. The 4 remaining skips are the pre-existing,
  environment-specific cases (root can read chmod-0 files) unrelated to
  the GUI.
- Manually traced the cross-thread SQLite risk: `MainWindow.connection`
  is opened on the GUI thread and must not be used from the background
  worker thread (sqlite3 connections are single-thread by default). Both
  worker functions now open and close their own short-lived connection
  to the same database file instead of sharing `self.connection` — this
  was caught and fixed during this run via the new integration tests,
  which failed with `sqlite3.ProgrammingError` before the fix.

## Notes / decisions

- The GUI never touches hashing/comparison logic directly (section 5) —
  `main_window.py` only calls `core.baseline`/`core.scanner` and renders
  what comes back; `results_view.py` and `dialogs.py` are pure
  presentation.
- Baseline timestamps are stored as UTC ISO-8601 (unchanged from Run 3)
  and rendered in the viewer's local timezone for display
  (`_format_timestamp`), matching the spec's human-readable example
  ("August 26, 2026 12:31 AM") more closely than showing raw UTC.
- The results table's "Timestamp" column (section 12) uses the scan's
  completion time for every row, since `ScanResult` records a per-file
  status but not a per-file timestamp — only the scan as a whole has
  one. Documented here rather than adding a per-file timestamp field not
  required by section 6.3's data model.
- This run added `python3-tk` and a disposable Python 3.12 venv to this
  container purely for verification (not part of the shipped
  application) — the project's own `requirements.txt` is unchanged, and
  the default Python in this container still lacks `tkinter`, so GUI
  tests continue to skip gracefully here as they did in prior runs.
