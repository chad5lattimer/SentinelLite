## Completed this run

- `core/models.py`: `FileRecord` dataclass (`path`, `sha256`, `size`,
  `modified_time`), per `PROJECT_SPEC.md` section 6.1/6.2. Paths are
  stored relative to the monitored root, POSIX-style, for portability.
- `core/hasher.py`: `calculate_sha256()` -- incremental, chunked SHA-256
  hashing via `hashlib`, using the configurable `DEFAULT_HASH_CHUNK_SIZE`
  (1 MiB) from `config.py`. Never loads a full file into memory (section
  7.2). Raises `OSError` on unreadable files; does not itself decide how
  to handle that (left to callers, per section 7.3).
- `core/filesystem.py`:
  - `iter_files()`: recursive traversal (`os.walk`) yielding every regular
    file under a root directory. Unreadable directories are logged and
    skipped rather than aborting enumeration (section 8.3). Symbolic
    links are not followed by default -- neither symlinked directories nor
    symlinked files are traversed/hashed (section 8.2; documented in the
    module docstring) -- avoiding symlink cycles and escaping the
    monitored root. `follow_symlinks=True` is available as an explicit
    opt-in.
  - `build_file_records()`: enumerates + hashes a directory tree, returning
    an `EnumerationResult(records, errors)`. Per-file read failures
    (permission errors, files deleted mid-scan, etc.) are logged and
    collected as `FileReadError` entries instead of raising -- the scan
    continues with the remaining files (sections 7.3/8.3). Accepts an
    optional `on_progress(done, total, relative_path)` callback so the
    GUI's background scan thread (Run 5) can display progress (section
    13) without this module knowing anything about the GUI.
- `tests/test_hasher.py`: same-content → same hash, modified content →
  different hash, empty file, a reference-vs-`hashlib` check, hashing
  across many small chunks (chunk-boundary correctness), a missing file
  raises `OSError`, and an invalid chunk size is rejected.
- `tests/test_filesystem.py`: recursive enumeration matches the expected
  set of relative paths; `build_file_records()` produces correct
  hash/size/mtime metadata and progress callbacks; an unreadable file is
  recorded as an error while the scan continues; an unreadable
  subdirectory is skipped without crashing; symlinked files/directories
  are not followed by default. The permission-based tests are skipped
  automatically when running as root (permission bits are meaningless for
  root) or on Windows (different permission model) -- verified separately
  by running the suite as an unprivileged user (`nobody`), where all
  permission/symlink cases exercise their intended code path and pass.

## Notes / decisions

- Symlink policy (section 8.2, "document the chosen behavior"): symlinked
  files and directories are skipped entirely by default rather than
  hashed or recursed into. This is the more conservative reading of "avoid
  recursively following symbolic links unless explicitly determined to be
  safe" -- a symlinked *file* is still a way to point the scanner outside
  the monitored root, so it is excluded too, not just symlinked
  directories. `follow_symlinks=True` exists for a future, explicitly
  opted-in use case but is not exposed in the GUI (out of scope for this
  run).
- `core/models.py` intentionally holds only `FileRecord` for now.
  Scan-result models (NEW/MODIFIED/DELETED/UNCHANGED/ERROR,
  `PROJECT_SPEC.md` section 6.3) are deferred to Run 4 (`core/scanner.py`)
  per the scope-control rule (section 38) -- they belong conceptually to
  the comparison engine, not the enumeration/hashing engine.
- Progress reporting is implemented as a plain callback rather than
  anything thread- or GUI-aware, keeping `core/filesystem.py` independent
  of the GUI (section 5: "GUI must not contain hashing or filesystem
  comparison logic" -- the inverse also holds here: core logic stays free
  of GUI concerns). Threading/background-worker wiring is Run 5's job.
