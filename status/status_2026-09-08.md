## Completed this run

- `core/scanner.py`: the comparison and scan engine.
  - `compare_to_baseline()` -- the pure comparison step (section 10): takes
    a baseline plus a freshly-enumerated filesystem state and classifies
    every path as NEW, MODIFIED, DELETED, UNCHANGED, or ERROR. Kept free
    of filesystem I/O so it is directly unit-testable against in-memory
    records.
  - `run_scan()` -- enumerates and hashes a baseline's root directory
    (via `core.filesystem.scan_directory`, reusing the Run 2 engine) and
    delegates to `compare_to_baseline()`. Files that fail to read during
    the *current* scan become ERROR results (with the baseline hash still
    surfaced for context) rather than being mistaken for DELETED files.
  - `ScanResult` / `ScanSummary` dataclasses matching section 6.3 / 12.
  - `save_scan()`, `get_scan_results()`, `list_scans()` -- persistence and
    retrieval of scan history, delegating to the storage layer.
- `storage/repository.py`: extended with `insert_scan()`,
  `get_scan_results()`, `list_scans()`, and the `ScanMetadata` NamedTuple,
  writing to the `scans` / `scan_results` tables already defined in
  `storage/database.py` (schema was created in Run 3; query/write logic
  added now, per scope control). Every scan is inserted as a new row, so
  scan history accumulates rather than being overwritten.
- `tests/test_scanner.py`: the exact Run 4 acceptance scenario from

## Notes / decisions

- `compare_to_baseline()` treats a file present in both the baseline and
  the current-scan error list as ERROR, not DELETED -- an unreadable file
  is a different failure mode than a genuinely absent one, and section 7.3
  requires it be reported rather than silently reclassified.
- `run_scan()` does not persist anything itself; `save_scan()` is a
  separate call, mirroring the `create_baseline()` / `save_baseline()`
  split from Run 3. This keeps the scan pure-in-memory for testing and
  leaves the GUI (Run 5) free to show results before/without committing
  them to history if ever needed.
- `storage.repository` takes a `TYPE_CHECKING`-only import of
  `core.scanner.ScanResult` (with a local import inside
  `get_scan_results()`) to avoid a circular import, since `core.scanner`
  already imports `storage.repository` for persistence.
- Results are sorted by path in `compare_to_baseline()` for stable,
  deterministic output -- useful for tests and for a future results table
  that defaults to alphabetical order before the user applies sorting.
