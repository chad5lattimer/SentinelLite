## Completed this run

- `core/scanner.py`: the scan engine.
  - `ScanFileResult` -- a single file's outcome (`status`, `baseline_hash`,
    `current_hash`, `size`, `error_message`), per section 6.3.
  - `ScanSummary` -- a completed scan's full result set plus derived
    counts (`modified_count`, `new_count`, `deleted_count`,
    `unchanged_count`, `error_count`) and `has_changes`.
  - `run_scan()` -- loads the current directory state via
    `core.filesystem.scan_directory()`, compares it against a saved
    `Baseline` following the exact logic in section 10 (NEW: current only;
    DELETED: baseline only; MODIFIED: both present, hashes differ;
    UNCHANGED: both present, hashes match), folds in ERROR results for any
    file that could not be read during the scan (section 7.3 -- a read
    failure never aborts the scan), and persists the result as new scan
    history via `storage.repository.insert_scan()`.
  - Scanning defaults to the baseline's own `root_directory` but accepts an
    explicit `root` override, and forwards `progress_callback`/
    `chunk_size` straight through to the filesystem engine for the GUI
    progress display Run 5 will add (section 13).
- `storage/repository.py`: added scan-history data access --
  `insert_scan()` (writes one `scans` row plus one `scan_results` row per
  file), `get_latest_scan_id()`, `get_scan_metadata()`, and
  `get_scan_results()`. Follows the Run 3 pattern: every scan is a new row,
  nothing is overwritten, so history accumulates across repeated scans
  against the same baseline.
- `tests/test_scanner.py`: the full Run 4 / section 33 acceptance scenario
  (A modified, B deleted, C unchanged, D new -> exactly those four
  statuses), plus per-status hash-field checks (a DELETED file carries no
  current hash, a NEW file carries no baseline hash), a no-changes scan,
  unreadable-file handling (ERROR without aborting the rest of the scan),
  scanning against an explicit alternate root, an unsaved-baseline guard,
  and scan-history persistence/reload round-tripping including multiple
  scans accumulating independent history rows.

## Notes / decisions

- A test-setup note worth recording: the scanner tests keep the SQLite
  database file as a *sibling* of the monitored directory, never inside
  it. Placing the database inside a directory being scanned makes the
  scan detect the database file's own growth (from the baseline/scan
  writes themselves) as a MODIFIED file -- a self-referential artifact of
  the test, not a scanner defect. This mirrors real usage, where the
  database lives in the application-data directory (section 22), never
  inside a user-monitored folder, so it does not need special-casing in
  `core.scanner` itself.
- `run_scan()` requires a saved baseline (`baseline.baseline_id` set)
  rather than accepting an in-memory one, since a scan's history row must
  reference a `baseline_id` foreign key (section 14). This keeps the
  function's contract simple: callers create-then-save a baseline first
  (Run 3), then scan against it.
- Kept `ScanSummary.scan_id` typed as optional (mirroring
  `Baseline.baseline_id`) for symmetry and future flexibility, even though
  `run_scan()` always returns a persisted summary today.
