`customtkinter` installed. They were installed (`pip install pytest
pytest-cov customtkinter`; `apt-get install python3-tk` for the system
Python 3.12, used via a local venv for real-display GUI tests under
`xvfb-run`) so the suite — including the real-display GUI tests — could
actually run, matching how prior runs verified the app.

Baseline (before any change), confirming no regressions:
- Headless: 56 passed, 31 skipped — matches Run 12's recorded numbers exactly.
- Real display (Xvfb): 93 passed, 4 skipped — matches Run 12's recorded numbers exactly.

Coverage (`--cov=core --cov=gui --cov=storage --cov=reports --cov=config`,
real display) showed 99% overall, with two concrete, previously-unmeasured
gaps:

- `config.py` lines 60-62 and 65: the Windows (`%LOCALAPPDATA%`, with and
  without the env var set) and macOS branches of
  `_default_app_data_dir()` (section 22). These can't execute on this
  Linux environment without deliberately reaching them.
- `core/filesystem.py` line 53 and lines 116-118: the `os.walk`
  `onerror` callback (section 8.3, "permission errors must not terminate
  the scan") and the `OSError` handling around hashing (section 7.3).
  The existing chmod-based permission test
  (`test_scan_directory_continues_after_permission_error`) correctly
  skips because this environment runs as root — the same root cause
  Runs 10-12 already found and worked around elsewhere (`storage`,
  `gui/dialogs.py`, `gui/main_window.py`, `gui/results_view.py`,
  `core/baseline.py`).

## What was done

Added 5 tests, all reaching the target branches by monkeypatching at
seams the production code already calls through (`sys.platform` /
`os.environ`, `os.walk`, `calculate_sha256`) rather than adding new
indirection or relying on real permission enforcement:

- `tests/test_foundation.py`: `test_default_app_data_dir_windows_with_localappdata`,
  `test_default_app_data_dir_windows_without_localappdata`,
  `test_default_app_data_dir_darwin`.
- `tests/test_filesystem.py`:
  `test_iter_file_paths_logs_and_continues_when_a_subdirectory_cannot_be_listed`,
  `test_scan_directory_records_error_when_hashing_raises_oserror`.

Result: real-display coverage is now 100% across every measured module
(`config.py`, `core/*`, `gui/*`, `storage/*`, `reports/*`) — 93 passed ->
98 passed. Headless: 61 passed, 31 skipped (the same 5 new tests, plus the
existing 26 GUI/display-dependent skips). No production code was changed.

## Pre-existing flake observed (not fixed, out of scope for this run)

While confirming the fix under repeated runs, one intermittent failure was
observed in `tests/test_gui_integration.py::test_full_workflow_select_baseline_modify_scan`:

```
RuntimeError: main thread is not in main loop
```

raised inside `gui/main_window.py`'s `_start_background_task.run()`, when a
background scan thread's `self.after(...)` call races a test's window
teardown. It reproduced once in one run *under `pytest-cov`'s line-tracing
overhead* and did not reproduce in 8/8 runs without `--cov` (5 plain runs,
3 more under `--cov`, all after this run's changes were in place) or in
the pre-change baseline. This is pre-existing, timing-dependent test-harness
behavior, not something introduced by this run's tests (which touch
`config.py` and `core/filesystem.py`, not `gui/`), and it does not
reproduce under the spec's plain `pytest` invocation. It is recorded here
rather than fixed, since root-causing and hardening a background-thread/
window-teardown race is a materially different task from this run's
coverage-gap objective and would expand scope (PROJECT_SPEC.md section 38).
A future run could investigate whether `gui/main_window.py` should guard
`self.after(...)` calls against a destroyed window (e.g. checking
`winfo_exists()`), which would also harden the real application against a
user closing SentinelLite while a scan is in progress.
