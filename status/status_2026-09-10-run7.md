## Notes / decisions

- **UI polish**: reviewed `gui/main_window.py`, `gui/results_view.py`,
  and `gui/dialogs.py` end-to-end against section 11 (design goals: clean,
  modern, minimal, readable, beginner-friendly, responsive) and section 23
  (plain-language UX: "File Changes" not "Cryptographic Integrity
  Differential Analysis", etc.). No changes were made — the existing
  implementation already uses plain-language labels and status messages
  matching the spec's exact examples (e.g. "✓ No Changes Detected",
  "Baseline Ready"), and adding cosmetic changes with no corresponding
  spec requirement would be scope creep per section 38.
- **Why a non-Windows build counts as verification here**: the spec
  (section 4.2) recommends but does not require Windows for *development*
  — only the final deliverable is Windows-targeted. Since this
  environment has no Windows machine available, the most rigorous
  available check is exercising PyInstaller's actual dependency analysis
  and bootloader packaging against the real `app.py`/`core`/`gui` code,
  which is platform-independent risk (missing hidden imports, bad entry
  point, etc.) — and then running the resulting binary. Windows-specific
  packaging risk (Tcl/Tk bundling quirks, antivirus false positives on
  the bootloader, `%LOCALAPPDATA%` resolution) cannot be exercised here
  and should be spot-checked the first time `build_exe.bat` is run on a
  real Windows machine.
- No code in `core/`, `storage/`, `gui/`, or `reports/` was changed this
  run beyond the new test — Runs 1-6 already satisfied every Run 7
  code-facing acceptance criterion; this run's job was to *verify* that
  (per section 37: "Do not assume previous work was completed correctly.
  Verify it.") and close the packaging/documentation/formal-acceptance-test
  gap.
